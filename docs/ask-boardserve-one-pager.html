Ask BoardServe

A chat box that answers questions about a board's own data with a chart and one honest sentence.

What it is

Ask BoardServe lets a company secretary type a plain-English question about their board — attendance, outstanding actions, skills, what the papers said — and get back a chart with a single sentence explaining the notable thing in it.

It is for the person who prepares the board pack: someone who already has a fixed analytics dashboard and keeps having to answer the questions it does not cover.

The screens
in order
  1. 01

    Passcode

    One field and a button. Real board data sits behind it, so nothing loads until the code is right. Wrong code says so in plain words.

  2. 02

    The chat

    The whole product. An empty page with a question box at the bottom and four or five example questions above it, so nobody has to guess what it can do. Answers stack up the page: chart, then one sentence, then a small note of where the number came from. Every answer carries a Pin button.

  3. 03

    The pinned board

    Everything pinned, in a grid, in the order it was pinned. Each tile keeps its chart, its sentence and the question that produced it. You can remove a tile. That is all it does.

Three screens. There is no settings page, no history, no login, no account.

One journey

A company secretary is drafting the governance section of the annual report. She has forty minutes.

ArrivesTypes the passcode. Lands on an empty chat.
She asks“What actions are overdue, and who owns them?”
Gets backA bar chart of overdue actions by owner, and one sentence: Nine actions are overdue when you work it out from the due dates, though only seven are recorded as overdue in the log; the Chair holds four of them.
She noticesthe gap between nine and seven, and pins the chart.
She asks“Which of those have been sitting longest?”
Gets backThe same nine, re-sorted by days past due, as a horizontal bar chart. She did not have to repeat the word “overdue” — it remembered.
She asks“How many of our directors are qualified accountants?”
Gets backA refusal, and the reason: the skills audit records how confident directors feel, not what qualifications they hold. No chart, no guess.
She leaveswith two pinned charts and a paragraph she can defend in a board meeting.
What happens
when she asks
  1. The question goes to the model with a list of tools. Attendance, actions, skills, search the papers, and refuse. The model's only job here is to pick one and fill in its settings.
  2. The chosen tool runs over the real files. Ordinary code. It reads the attendance records, the action log, the skills sheet. It does the arithmetic and returns numbers, plus a note of which rules it applied.
  3. The numbers come back as a chart. The tool says which shape fits — bar for a ranking, line over time — and the screen draws it.
  4. The model writes one sentence about those numbers. It is shown the result and asked for the notable finding. It is never shown the raw data, so it has nothing to do arithmetic on.
  5. The question and answer are kept for the next turn so a follow-up can say “those” and mean something.
The one rule everything else follows: tools compute, the model narrates. No number on the screen is ever produced by the language model. If it cannot be traced to a tool that ran, it does not get shown.
Three days
Day one

Numbers you can trust

  • Prove the model picks the right tool, in a script, before any screen exists
  • Write the tools and check every figure against the totals in the data
  • Bare chat page, charts drawing on screen
By the end of it: an ugly page that answers eight real questions with correct charts.
Day two

Judgement

  • Board papers searchable, so document questions get answered from the text
  • Refusals working, and tested against questions designed to trip it
  • Follow-up questions keep their context
  • Pinning, and the pinned board
By the end of it: it knows what it cannot answer, and says so. This is the day the product becomes defensible.
Day three

Fit to show

  • A test file of fixed questions and expected answers, run in one command
  • Passcode, deployment, loading states, sensible errors
  • The design pass
  • The second organisation's data loaded, to prove nothing was hard-coded
By the end of it: a live link, a passcode, and evidence it is right rather than a claim that it is.
Not building
  • ×Accounts, roles or user management.One shared passcode. There is one user in this story and she is in the room.
  • ×Shareable public dashboard links.A URL that exposes board data with no passcode is a governance problem, not a feature. Cut, not deferred.
  • ×Image export of charts.Screenshots exist. Nobody is blocked without this.
  • ×A vector database for three documents.Three short papers fit in a single prompt. Building search infrastructure for them is building for a scale that does not exist.
  • ×Caching and response storage.Nothing is slow enough or expensive enough yet to be worth the bugs.
  • ×Editing, renaming or rearranging pinned tiles.Pin and unpin. Anything more is a document editor.
  • ×Guessing.Where the data does not answer the question, the answer is that it does not answer the question.
Where this could still go wrong. The whole product rests on the model choosing the right tool and refusing cleanly. That is worth proving in an hour with a script, before a single screen is built — because if it does not hold, everything built on top of it has to be rebuilt.
